# Netlify plugin TTL cache

A Netlify plugin for preserving immutable build assets across deploys.

## Why This Exists

Netlify deploys typically replace the published asset set with the output from the latest build. That is usually correct, but it can be a problem for apps that ship fingerprinted JavaScript, CSS, and other static files and then load those assets lazily at runtime.

The common failure mode is:

1. A user loads version `A` of the app.
2. A new deploy publishes version `B`.
3. The running app from version `A` later requests an older chunk or asset by its hashed filename.
4. That file no longer exists in the latest deploy output.
5. The browser gets a 404 and the app fails with a chunk-loading or dynamic-import error.

This plugin reduces that problem by keeping older built assets around for a limited time instead of replacing them immediately.

## How It Works

The plugin hooks into Netlify's build lifecycle in two phases:

1. Before the build, it restores the previously cached build output directory.
2. It removes files that are too old or explicitly excluded.
3. It copies the remaining cached files into a temporary directory.
4. Your site build runs and writes the new deploy output.
5. After the build, it copies the cached files back into the build output without overwriting newly generated files.
6. It saves the merged output back into the Netlify cache for the next deploy.

In effect, the current deploy contains:

- the assets generated by the latest build
- older immutable assets that are still within the retention window

That makes it safer to deploy applications where clients may continue requesting older hashed assets for some period after a new release goes live.

## When To Use It

This plugin is a good fit when:

- your build output contains fingerprinted assets such as `app.abcd1234.js`
- older assets can still be requested by users with an already-loaded page
- you want a short retention window for previous deploy artifacts

It is a poor fit when:

- filenames are reused across deploys instead of being content-hashed
- your output directory should contain only the latest build artifacts
- keeping old files around would create correctness or compliance problems

## Publishing

`main` is source-only. Run the manual GitHub Actions workflow to build the package and force-update the `release` branch with the installable artifact.

To publish the `release` branch:

1. Push the workflow file to the default branch.
2. Open the repository's `Actions` tab in GitHub.
3. Select the `Publish release branch` workflow.
4. Click `Run workflow`.

The workflow installs dependencies, runs lint/tests, builds `dist/`, and force-pushes the installable package files to the `release` branch.

## Usage

Install the plugin from the `release` branch:

```sh
npm i -D github:ChipDrop/netlify-plugin-ttl-cache#release
```

Tracking the branch head is intentional: when a new commit lands on `release`, you can pick it up in the consumer by running `npm install` (which re-resolves the git ref and updates `package-lock.json`) and committing the updated lockfile. Netlify builds use `npm ci`, which installs strictly from the lockfile, so the lockfile bump is what actually moves the consumer to the new plugin commit — not the branch name on its own.

If you need strict reproducibility instead, pin a commit SHA directly:

```sh
npm i -D github:ChipDrop/netlify-plugin-ttl-cache#<commit-sha>
```

Add the plugin to your `netlify.toml`:

```toml
[[plugins]]
package = "@chipdrop/netlify-plugin-ttl-cache"
  [plugins.inputs]
  path = "build"
  ttl = 90
```

If your build output lives somewhere other than `build`, set `path` accordingly.

## Configuration Example

```toml
[[plugins]]
package = "@chipdrop/netlify-plugin-ttl-cache"
  [plugins.inputs]
  path = "dist"
  ttl = 30
  exclude = "\\.html$"
```

The example above keeps old files from `dist/` for up to 30 days while excluding HTML files from retention. Excluding HTML is often useful because HTML entrypoints should generally come only from the newest deploy.

## Input Reference

### `path`

_Build output directory._

**type:** `string`

**default:** `"build"`

This should point to the directory Netlify will publish for the site.

### `ttl`

_Maximum age (days) of files in cache._

**type:** `number`

**default:** `90`

Files older than this threshold are deleted before the cached assets are merged into the new build output.

### `exclude`

_Regular expression [string pattern](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/RegExp) for files to exclude._

**type:** `string`

**default:** `n/a`

Any cached file whose path matches this pattern is removed before merge. This is useful for files you never want to preserve across deploys, such as HTML documents, manifests, or other non-immutable entrypoints.
